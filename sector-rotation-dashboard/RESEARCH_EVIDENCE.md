# Weekly research evidence contract
The only weekly research edit is `site/data/research-evidence.json` (public; no personal data). Keep schema_version 1, reviewed_at ISO date of actual review, and events array. Preserve existing event IDs and dated records; update state to resolved/superseded instead of deleting. Add an updated event with its own ID when facts change. A structural active record remains visible; routine active evidence rolls into supporting details after 28 days relative to reviewed_at. Two recent active items max per card, older evidence expandable. Medium materiality stays within cards; high materiality can enter Overview priorities (once per event). Source URLs HTTPS, issuer/regulator primary wherever possible; date is event date, not publication date if different; fact and implication distinct. kind confirmed/guidance/reported; materiality high/medium; state active/resolved/superseded; structural true/false; impacts entries symbol,tab,key,title,tone,implication, optional overview:true and optional assessment:{status,reason}. tone positive/negative/mixed/neutral. Only confirmed high-materiality active events with explicit reason may override assessment; no overriding reported figures. Driver statuses positive/mixed/negative/unknown; risk high/watch/disclosed/clear/structural; thesis support/watch/pressure/neutral/unknown. Newest explicit qualifying change wins; resolve or supersede when no longer justified. Do not promote a single event into a sustained trend. Use the exact card keys from stocks.js: driverGroups names; financial insight IDs earnings,leverage,growth,shares,cash,capex,runway; risk exposureDimensions or filing IDs (new descriptive risk key permitted for material unquantified exposures); peer key consolidated (AMZN aws/retail/ads/consolidated); thesisConfig checks exact first string. Avoid duplicate interpretations, no standalone news section. If source unavailable, do not invent or update. No private holdings or notes. Update reviewed_at after genuine review, even no material changes. Keep the existing company snapshots separate; weekly changes only to this JSON unless user asks otherwise. Validate JSON, tests, commit using latest main SHA with compare-and-swap, verify workflow deployment or explicitly report pending/failure.

## Weekly catalyst review

Review the three watchlist topics for each of IBKR, HOOD, AMZN, GOOGL, NVDA, KTOS and OKLO. Write updates to the optional `catalysts` array in the same evidence JSON. Match the `symbol` and the exact catalyst name (the first string in its `thesisConfig` entry) in `key`. Include `date` (ISO), `headline`, `fact`, `assessment`, `tone` (positive, negative, mixed or neutral), `state` (active, resolved or superseded), and `sources` (primary HTTPS links with labels). Optional `metrics` are pairs of display label and value, including the period or basis where needed.

Add `next` with a label and `status` of expected or scheduled. For a scheduled event, include its ISO `date` and the official calendar `url`. Give an approximate window in the label when timing is inferred, or omit `next` when timing is unclear. Review any elapsed next dates and update the follow-up. Keep the latest relevant development active until a newer sourced development replaces it or it is resolved. The watchlist shows the latest active record for each topic regardless of age. If a topic has no verified update, keep the existing record or leave an uncovered topic empty. Include material catalyst changes in the weekly summary.

## Overview ownership activity

Keep the optional `ownership` object keyed by ticker. Each snapshot has a `reviewed_at` date and may have `insiders`, `stakes` and `comparison`. Insider and stake rows require `name`, `kind`, transaction or position `date`, `filed` date, display `value`, `detail` and the HTTPS filing `url`. Use insider kinds buy, sell, planned and other. Review Form 4 footnotes and amendments. Deduplicate executions and amended filings. Mark discretionary sells as `material:true` only after reviewing stake reductions, and provide a stable `personId` for the 30-day distinct-seller count. Use 13D or 13G for stake rows and describe the filer type when supported by the filing.

Use `comparison` only for comparable, split-adjusted share counts across matching stock classes and deduplicated managers. Include ISO `quarter` and `priorQuarter`, integer `netShares`, `managers`, `added`, `trimmed`, and an HTTPS `url` for the underlying filing data. Optional `groups` contain `label` and integer `netShares` and must sum to the total. Include a mixed or unknown group where the strategy is unverified. These are reported holdings changes. Preserve missing coverage and never infer current flows from the comparison.
